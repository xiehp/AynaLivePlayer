# 开发规范与同步规则

这份文档分成两部分：

1. 当原作者后续继续修改仓库时，我们如何把自己的改动安全地覆盖回去。
2. 这个项目当前已经呈现出来的代码风格和行为准则。

## 一、与作者同步修改时的覆盖规范

这个项目不是我们独占维护的，所以最重要的原则不是“直接覆盖”，而是“保留自己的改动可重放”。

### 1. 基本原则

- 不直接在主工作区里做不可追踪的大改。
- 每次我们的修改尽量集中在少量文件和少量职责上。
- 所有定制点都要能被重新应用，而不是一次性手工拼出来。
- 先保留原作者版本，再叠加我们的定制层。

### 2. 推荐工作方式

建议把我们的修改当成一组可重复应用的补丁，而不是“最终成品”。

推荐流程是：

1. 先保留一份当前仓库基线。
2. 我们的定制修改尽量拆成小块。
3. 作者更新后，先同步最新代码。
4. 再把我们自己的补丁重新应用到最新版本上。
5. 如果冲突，只解决我们改过的那一小段，不扩大重写范围。

### 3. 具体执行规范

建议形成下面的固定动作：

- 每次开始定制前，先记录基线提交或导出补丁。
- 每次改动后，保留变更说明，写明涉及哪些文件、改了什么逻辑。
- 作者更新后，先对比差异，再重新套用我们的补丁。
- 如果作者改动覆盖了我们的逻辑，优先做三方合并，而不是直接重写。
- 如果某个定制点冲突太多，优先抽象成配置或独立模块，减少和作者主线的耦合。

### 4. 建议的分层策略

为了让后续覆盖更容易，建议把我们的改动分成三类：

- 配置层：新增配置项，尽量不改核心流程。
- 策略层：权限、黑名单、重连策略等可替换判断逻辑。
- 接入层：只在入口处挂钩，不直接改太多底层实现。

这样做的好处是：作者如果继续改界面、文案、细节逻辑，我们通常只需要重新应用策略层和接入层，而不是整仓库重做。

### 5. 最小改动原则

后续所有定制都尽量遵守最小改动原则：

- 原作者文件只保留必要的介入点，尽量只加极少量代码。
- 新增逻辑优先放到我们自己的新文件里，而不是直接塞回原文件。
- 原文件里的改动尽量只负责调用、注册、转发或挂载。
- 真正的业务实现、判断规则、工具方法、配置解析都放在新文件中。
- 如果某个功能必须改原文件，就只改一小段入口代码，避免大面积重写。

这样后续作者即使继续改原仓库，我们也只需要知道“哪里要加几行挂载代码”，然后把完整功能仍然放在自己的新增文件里，补丁就更容易重新打回去。

### 6. 冲突处理原则

- 如果作者改的是格式或文案，优先接受作者版本。
- 如果作者改的是核心逻辑，先判断是否影响我们的定制需求，再决定是否保留作者版本。
- 如果作者改动和我们的定制都合理，优先把我们的逻辑做成开关或配置，而不是硬合并成一条分支。
- 任何时候都不要用“整文件覆盖”作为默认方案。

### 7. 最适合这类项目的实际做法

这类项目最稳妥的方式，是把定制内容单独记录成一份“补丁清单”或“改造清单”，每次作者更新后按清单重新应用。

建议以后固定保留这些内容：

- 改动目的
- 涉及文件
- 改动逻辑
- 是否依赖作者原有实现
- 冲突时的优先级

这样即使作者不通知我们，我们也能在拉到新版本后快速判断哪些定制需要重新覆盖。

## 二、当前项目已有的代码规范和行为准则

这个仓库本身已经表现出一些比较稳定的风格，可以当成后续统一开发的参考。

### 1. 语言和工程基础

- 项目使用 Go。
- 模块名是 [go.mod](go.mod) 里的 `AynaLivePlayer`。
- 目标构建包含桌面 GUI，底层依赖 Fyne。
- 代码里广泛使用事件总线做模块解耦。

### 2. 目录分层比较明确

当前仓库明显分成几层：

- [app/](app/)：程序入口。
- [internal/](internal/)：初始化和运行时核心逻辑。
- [core/](core/)：业务核心、模型和事件定义。
- [gui/](gui/)：界面层。
- [pkg/](pkg/)：公共基础能力。
- [plugin/](plugin/)：功能插件层。
- [config/](config/) 和 [assets/](assets/)：配置与资源。

这种分层说明项目倾向于“职责拆分”，而不是把所有逻辑堆在一个入口文件里。

### 3. 命名风格

仓库里常见的命名方式是：

- 包名短且小写，例如 `eventbus`、`logger`、`config`、`player`。
- 结构体和导出方法使用大驼峰。
- 配置结构体通常使用前缀或明确语义，例如 `General`、`BaseConfig`。
- 事件名使用字符串常量，例如 `cmd.liveroom.operation`、`update.liveroom.status` 这种风格。

### 4. 配置处理方式

项目对配置的处理比较统一：

- 使用结构体承载配置。
- 通过 `Name()`、`OnLoad()`、`OnSave()` 一类接口把配置挂入统一系统。
- 读取时从 ini 或 JSON 载入。
- 保存时集中回写到文件。

这说明仓库偏向“声明式配置”，而不是到处手动读写零散文件。

### 5. 事件驱动风格

仓库里大量逻辑通过事件总线串联，例如：

- 订阅事件后异步处理。
- 发布事件通知其他模块。
- 通过 Reply 机制做请求响应。

从代码注释里也能看出一个明确的行为准则：事件处理函数应该尽量非阻塞，长逻辑不要卡住主流程。

### 6. GUI 与业务分离

界面层主要负责展示和触发动作，不直接承担太多业务计算。

例如：

- GUI 页面负责按钮、标签、表单和显示。
- 真正的播放、点歌、房间控制逻辑在 internal、core 或 plugin 里。

这说明项目风格上倾向于把“显示”和“处理”分开。

### 7. 插件化思路

点歌、切歌、音量、登录、文本信息、WebSocket Hub 这些能力都被拆成插件。

这说明仓库本身已经在做“功能模块化”，后续新增能力最好也按插件或独立模块的方式接入。

### 8. 资源和构建习惯

- 构建脚本放在 [Makefile](Makefile)。
- 资源通过 `fyne bundle` 生成。
- 打包时会处理 `assets/`、`music/`、`config/` 等资源目录。

这说明项目对资源路径比较敏感，后续新增文件时要注意是否需要同步到打包流程里。

### 9. 现有实现里的实用准则

从代码可以看出几个明显的习惯：

- 先保证能运行，再逐步补完整行为。
- UI 和核心逻辑用事件连接，减少直接依赖。
- 配置项尽量默认有值，避免启动时空配置崩溃。
- 关闭时主动保存状态，减少用户配置丢失。

### 10. 对我们后续改造的约束

以后我们做定制时，最好也沿用这些准则：

- 不破坏事件驱动结构。
- 不把业务逻辑塞进 GUI。
- 新功能优先做成可配置。
- 与作者现有风格保持一致，少做大面积重构。

## 三、简化后的执行口径

以后可以把我们的工作口径固定成一句话：

“先保留作者主线，再把我们的定制做成小补丁、小模块、小配置，更新后按清单重放。”

## 四、文档化要求

以后我们每做一件事情，都尽量同步留下对应的文档记录。原因很直接：这个项目后续还会继续变化，如果不记录，后面很难判断某个改动为什么存在、依赖什么、该不该保留。

### 1. 每次变更都要留记录

不管是改代码、补配置、加规则、修 bug，还是做重构，都建议留下最少一份记录。

至少要写清楚：

- 做了什么
- 为什么做
- 改了哪些文件
- 影响了哪些行为
- 后续如果作者更新，哪些地方需要重新打补丁

### 2. 文档优先级

建议把文档分成三层：

- 总规范：长期不变的原则，例如最小改动原则、补丁重放原则。
- 方案文档：某个需求的设计方案，例如重连、权限、黑名单。
- 变更记录：某次具体修改的结果，例如改了哪个函数、加了哪个配置。

### 3. 文档写法原则

- 文档要短，先写结论，再写理由。
- 文档要能落地，不能只写抽象口号。
- 文档要对应到文件或模块，不要只写空泛描述。
- 文档要能帮助后续重放补丁，所以要尽量明确“入口在哪里、实现放哪里、如何恢复”。

### 4. 推荐维护方式

建议以后固定维护三类文件：

- `docs/development-norms.md`：规范和原则。
- `docs/customization-plan.md`：定制方案和模块拆解。
- `docs/change-log.md`：每次改动的简要记录。

如果某次改动比较大，可以单独再拆成一个专题文档。

### 5. 最低记录标准

即使只是很小的修改，也至少记录一条简短说明：

- 日期
- 改动目标
- 改动范围
- 是否需要重放

这样以后回头看仓库时，就不会只看到代码，而不知道代码为什么会变成现在这样。
